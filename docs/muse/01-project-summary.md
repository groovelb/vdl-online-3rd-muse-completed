## 1. 한 줄 요약

> 모아 둔 레퍼런스에서 디자인 토큰을 뽑되 토큰마다 출처와 이유가 함께 남아, 결정의 주도권이 AI가 아니라 사람에게 있는 디자인 시스템 빌더.

태그라인: 바이브 디자인을 위한 영감을 관리하세요.

---

## 2. 배경과 목적

- **문제 또는 기회**: AI 디자인 도구는 결과만 주고 근거를 주지 않는다. 52건 출처를 모은 정성 리서치에서 네 갈래 문제가 반복해서 나왔다. 결정 근거가 남지 않는 것, 입력이 하나뿐이라 결과가 다 비슷해지는 것, 사용량과 편집에서 통제권을 잃는 것, 그리고 AI가 사람의 craft를 대체한다는 전제다. 네 갈래 모두 "왜 그렇게 정했는가"를 보관하지 않는 데서 나온다.
- **왜 지금, 왜 우리**: 토큰을 뽑아 주는 도구는 이미 여럿이지만, 토큰과 그 토큰을 고른 이유를 같은 산출물에 담는 도구는 아직 드물다. 이유를 담으려면 결과 화면이 아니라 입력 지점의 설계를 바꿔야 하고, 그것이 이 프로젝트의 자리다.
- **기대 효과**: 사용자가 결과를 "AI가 만든 것"이 아니라 "내가 정한 것"으로 인식한다. 외부 AI 코딩 도구에 토큰과 결정 로그를 함께 넘길 수 있어 옮기는 중에 의도가 사라지지 않는다. 레퍼런스를 모으는 습관과 프로젝트 단위 큐레이션이 한 도구 안에서 이어진다.

## 3. 정체성

### 3.1 핵심 가치 (최대 3)

| 이름 | 한 줄 | 반대말 (하지 않는 태도) |
|---|---|---|
| Traceability (추적성) | 모든 결정에 출처와 이유가 붙는다 | 결과만 건네는 블랙박스 |
| Authorship (주도권) | 고르는 사람은 끝까지 사용자다 | 한 번에 다 정해 주는 자동 완성 |
| Restraint (절제) | 도구는 뒤로 빠지고 소재가 앞에 선다 | 존재감을 과시하는 도구 |

### 3.2 태도 키워드 (최대 5, 단어만)

투명함 · 절제 · 미니멀 · 공간감 · 이미지 우선

### 3.3 포지셔닝 (선택)

| 축 | 우리의 선택 | 반대 축 |
|---|---|---|
| 산출물 | 토큰과 결정 로그를 함께 | 결과 토큰만 |
| 입력 | 여러 레퍼런스의 레이어 조합 | 프리셋 하나 고르기 |
| 결정 주체 | 사용자가 단계마다 고른다 | AI가 한 번에 정한다 |
| 톤 | 소재가 주인공인 중립 화면 | 도구의 색이 앞서는 화면 |
| 범위 | 토큰까지, 코드는 외부 도구가 | 코드 생성까지 한 도구가 |

## 4. 사용자와 다루는 대상

### 4.1 사용자

| 이름 | 누구인가 | 무엇을 원하나 | 주/보조 |
|---|---|---|---|
| 비디자이너 기획자 | 디자이너 없이 시안을 만드는 창업자 | 빨리 잡히는 컨셉 | 주 |
| 시니어 디자이너 | craft를 지키며 속도도 필요한 실무자 | 의도를 담은 큐레이션 수단 | 주 |
| 시스템 엔지니어 | 토큰을 코드로 옮기는 담당자 | 손대지 않고 들어가는 토큰 | 주 |
| 바이브 코딩 사용자 | AI 코딩 도구를 늘 쓰는 개발자 | 무시당하지 않는 결정 로그 | 보조 |

### 4.2 다루는 대상

| 이름 | 식별자 | 한 줄 정의 | 만드는 주체 | 개수 |
|---|---|---|---|---|
| 레퍼런스 | Reference | 태그와 추출값이 붙은 영감 이미지 한 장 | 사용자 | 많음 |
| 프로젝트 | Project | 모드와 의도, 노트를 묶은 작업 단위 | 사용자 | 몇 개 |
| 레퍼런스 활용 | ProjectReference | 한 레퍼런스에서 가져올 레이어 선언 | 사용자 | 많음 |
| 분석 결과 | AnalysisResult | 출처와 이유가 달린 토큰 묶음 | AI | 하나 |
| 사용자 설정 | UserSettings | 모델과 저장 방식, 화면 밝기 설정 | 시스템 | 하나 |
| 사용자 | User | 가입한 계정, 모든 자료의 소유자 | 사용자 | 하나 |

비고:

- 개수 값은 하나 / 몇 개 / 많음이다. 분석 결과와 레퍼런스 활용의 개수는 프로젝트 하나를 기준으로 센 값이다.
- 보고 있는 위치나 진행 중인 단계처럼 일시적인 상태는 다루는 대상이 아니다.

## 5. 핵심 과업 (3~5개)

| # | 과업 (동사형 한 문장) | 사용자 | 다루는 대상 | 필수/선택 |
|---|---|---|---|---|
| 1 | 영감 이미지를 모아 태그가 붙은 상태로 둔다 | 시니어 디자이너, 바이브 코딩 사용자 | Reference | 필수 |
| 2 | 의도와 레퍼런스를 단계마다 골라 결정을 좁힌다 | 전 사용자 | Project, ProjectReference | 필수 |
| 3 | 만들어진 토큰의 근거를 확인하고 다듬는다 | 시니어 디자이너, 시스템 엔지니어 | AnalysisResult | 필수 |
| 4 | 토큰과 결정 로그를 외부 도구로 가져간다 | 시스템 엔지니어, 바이브 코딩 사용자 | AnalysisResult, Project | 필수 |
| 5 | 무엇을 해 주는 도구인지 보고 계정을 만든다 | 전 사용자 | User, UserSettings | 필수 |

비고:

- 각 과업은 02에서 같은 번호의 시나리오 하나가 된다.
- 과업 2는 분석 실행까지 포함한다. 분석 결과를 읽는 일은 과업 3으로 나눴다.
- 과업 5는 원문에 없었다. 진입 경로와 가입 설계 부록을 근거로 추가했고 번호는 뒤에 붙였다.
- 사용자 칸의 "전 사용자"는 4.1절 네 이름 전부를 뜻한다.

## 6. 범위와 성공 기준

- **포함**: 이미지와 링크로 레퍼런스 모으기, 올릴 때 자동으로 붙는 레이어별 태그, 의도와 모드를 받는 단계형 생성 흐름, 레퍼런스별 활용 노트, 토큰 자동 분석과 결정 근거 보관, 레이어별 토큰 편집, 토큰과 결정 로그 내보내기, 가입과 로그인
- **제외**: 컴포넌트 코드 생성(토큰까지만 맡고 코드는 외부 도구가 맡는다) · 협업과 공유 · 모바일 전용 앱 · 정한 하나 외의 테마 포맷 · 레퍼런스마다 좋아한 이유를 묻는 입력(검증에서 효과 없어 폐기) · 분석 직전 확인 단계(진행 동작이 흡수) · 코드 직행 모드(시스템 모드가 흡수)
- **제약**: 분석은 외부 모델 호출에 의존하므로 비용과 지연을 감수한다 · 서체 추정은 이미지 기반이라 최선 근사다 · 저장 용량 전략이 필요하다 · 결과의 품질은 사용자가 올린 레퍼런스의 폭에 묶인다

운영 지표보다 "사용자가 결정했다고 느끼는가"를 먼저 본다.

| 성공 기준 | 확인 방법 |
|---|---|
| 첫 프로젝트에서 내보내기까지 3분 안에 도달 | 신규 사용자 과업 관찰 (잠정, Q1) |
| 의도 입력 평균 길이가 20자 미만에서 40자 넘게 | 입력 길이 분포 비교 (잠정, Q1) |
| 레이어 선택 수동 변경 비율 0%에서 30% 넘게 | 수동 변경 비율 집계 (잠정, Q1) |
| 토큰 근거를 펼쳐 보는 비율 60% 넘게 | 근거 펼침 비율 집계 (잠정, Q1) |
| 내보내기까지 간 비율 10%p 상승 | 기간 비교 (잠정, Q1) |
| 30일 재방문 비율 상승 | 기간 비교 (잠정, Q1) |
| 내보낸 결과가 외부 도구에서 무시되지 않는다 | 결정 로그 반영 여부 점검 (잠정, Q1) |
| 내보낸 값을 그대로 넣어 일관된 화면이 나온다 | 적용 후 눈으로 확인 (잠정, Q1) |

비고: 포함과 제약의 근거는 원문 기술적 범위 절이다. 목표 수치는 원문 지표 표의 값을 그대로 옮겼고, 확인 방법은 아직 측정한 적이 없는 제안값이다 (Q1).
